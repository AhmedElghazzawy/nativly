# 0005. Free-tier hosting: Render (API) + Neon (Postgres)

- **Date:** 2026-10-11
- **Status:** accepted

## Context
Phase 0 ends with the API deployed over HTTPS. Constraint: no paid services and no card on
file. The API ships as a Docker image and needs Postgres with pgvector (from Phase 3).

## Options
1. **Fly.io**: great Docker support and release commands, but requires a card.
2. **Railway**: simple, but the free allowance is a one-off trial credit.
3. **Render free web service + Neon free Postgres**: no card; Render builds our Dockerfile and
   terminates HTTPS; Neon's free tier doesn't expire and supports pgvector. Trade-offs: the
   Render instance sleeps after ~15 minutes idle (cold start ~30–60 s), and Neon scales to
   zero (first query after idle is slower).
4. **Render's own free Postgres**: expires after 30 days.

## Decision
Option 3. Infrastructure is declared in `render.yaml` (Blueprint):
- Docker web service in Frankfurt (next to Neon's `eu-central-1`), health check on `/health`.
- Auto-deploys only after GitHub CI passes on `main` (`autoDeployTrigger: checksPass`).
- `NATIVLY_JWT_SECRET_KEY` is generated by Render; `NATIVLY_DATABASE_URL` is entered once in
  the dashboard. No secret is ever in the repo.
- Migrations run in the container entrypoint (`scripts/start.sh`) because the free plan has no
  separate release step. Safe while we run a single instance.
- The app accepts Neon's URL as copied (`postgresql://…?sslmode=require&channel_binding=…`) and
  normalizes it for asyncpg. Use Neon's **direct** (non-pooled) endpoint: asyncpg's prepared
  statements don't work through PgBouncer in transaction mode.

## Consequences
- Zero cost; cold starts are acceptable for a portfolio-stage product.
- Revisit when there are real users: a paid instance (no sleep), a release-phase migration
  step, and Neon's pooled endpoint with `statement_cache_size=0`.
